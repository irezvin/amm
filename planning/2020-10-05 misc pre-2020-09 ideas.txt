2019-10-19

-   ? Amm.Collection.protectedProperty - objects that have this prop set are not deleted
    from the collection during setItems, splice
    -   how ArrayMapper + protected dest objects should behave?
    
    protectedPropery is a collection property that denotes name of the property of the objects inside
    the collection that mean that particular object shouldn't be deleted from the collection
    when items are replaced.
    
    Example: 
    
    coll.setProtectedProperty('dontDelete');
    coll.items[0].setDontDelete(true); // of course, this property should exist in advance
    coll.setItems([]); // regular collection will fully clear here....
    coll.length; // 1 // ...but coll.items[0] is left, because !!coll.items[0].getDontDelete()
    
    To clarify:
    
    a.  why do we need this outside of record collections? - initially I planned this to update
        autocomplete widgets from the server in a way that preserves selected items
    
    b.  as it was noted before, how should behave the ArrayMapper in the presence
        of protected objects in the destination:
        -   will have mismatched order of the source-dest objects, which we currently need
        -   if we have protected item (p.i.) left, that lost association with the source object,
            and then source object reappears in the source collection, we need to associate
            already existing p.i. with the source, instead of creating a new object.
    
-   (too complex) Amm.ArrayMapper.Multi: src is collection of collections
    
    - Amm.ArrayMapper.Recursive for treelike structures (expanding the idea),
        -   ability to descend into the members that fulfill some criterion
            (RecursiveFilter) 
    
2019-11-10

-   we have a Display Parent / Display Child hierarchy, but every element can
    have arbitrary number of views. Does it mean that the element can participate
    in multiple hierarchies at the same time? What can we do: leave main one,
    introduce others as additional ones?

    -   one Display Child can have multiple Display Parents
        (given the number of linked Amm.View.Html.Visual that have the elements
        in different containers)
        
    -   child: primaryDisplayParent (set/get); first one becomes the primary
        by default (if the view doesn't have `isPrimary`: true);
    -   container: add element views to the displayChildren instead of the elements
        themselves (we can easily access the element by view.getElement());
        
-   Builder: late instance linking

    fooProto: { id: foo, extObject: { __ref: 'bar' }, extObject2: { __ref: 'baz' } }
    barProto: { id: bar, extObject: { __ref: 'foo' } }
    bazProto: { id: baz }
    
    will be created in a regular order, but in the end it will be followed by
    
    foo.setExtObject(instances.bar)
    foo.setExtObject2(instances.baz)
    bar.setExtObject(instances.foo)
    
    OR

    make that if the mentioned object is already created, it will be immediately
    injected into the proto.

    This will allow to assign display parents to the elements/views
    inside the containers without the stupid hacks as `staticDisplayParent`.

    More to that, to avoid introduction of such stupid hacks in the future,
    we can introduce A. data-amm-x extension to link the element; B. a special
    case for the builder

    OR

    ghetto-approach: Amm.Element.locateComponent that asks views to search
    the component inside the definition of which our definition is nested.
    As a bonus, we'll be able to link elements by just putting DOM nodes inside each other.
    
    ?   Amm.View.Component: autoParent? 
    ?   Amm.Component.autoParent? - the parent component will be located every time?
    ?   static Amm.View.Html.locateParentComponent(element)?
    
    ?   how to implement this in a smooth and beautiful fashion?
    
-   adding to the above (simple and useful, since allows us
    to get rid of StaticDisplayParent):
    
    -   `autoParent` extension for the builder: searches component in the DOM
        hierarchy, links to it;
    -   Amm.Trait.LocateComponent, Amm.View.(Abstract|Html).LocateComponent
        -   by a timer or through a DOM observation locates the DOM node
            of an enclosing component; once found, the link to the parent
            component is established, and observation is stopped;
        -   observeHtml: true/false: enable non-stop observation.
