====== Amm.Builder ======
Created Monday 21 February 2022

Amm.Builder is a class that searches for constructor options of Amm.Elements and their Views in the DOM attributes, and creates instances of the elements and/or views.

===== Interface =====

==== Constructor ====
Amm.Builder = function([selector, ][options])
* selector: root node, or several root nodes, from which we start the DOM processing (CSS selector, or a jQuery node list)
* options: Builder properties

==== Properties ====
* **selector** - described above - top-level DOM nodes to process (CSS selector string, or a jQuery node list)
* **reportMode** - how to report the problems; is a bitmask; default value: PROBLEM_CONSOLE | PROBLEM_HTML (meaning both things):
	* Amm.Builder.PROBLEM_SILENT - ignore
	* Amm.Builder.PROBLEM_CONSOLE - produce the warnings in the JavaScript console
	* Amm.Builder.PROBLEM_HTML - create attribute data-amm-warning with the warning text in the problematic nodes
* **sel**: which top-level nodes should be searched for the presence of the ''options'' of Elements and Views. By default it's all nodes with any of the attributes **data-amm-id**, **data-amm-e**, **data-amm-v**, or **data-amm-x**.
* **selIgnore**: which nodes we should ignore inside the top-level nodes. By default it's the nodes with the attribute **data-amm-dont-build** and their descendants, elements with the attributes **data-amm-built** and **data-amm-iid** (see ''Amm.domHolderAttribute'').
* **topLevelComponent**:  Amm.Element or 'root'; null - all "top-level elements" (what is this? ones without the component? or ones those definitions weren't found inside nodes of the other elements? TODO - check) will have this element set as a parent ('root' means that the Amm.Root will become the parent element).
* **rememberElements**: boolean; false - should we add created elements to the Array provided as the ''elements'' argument
* **elements**: Array - filled-in if ''rememberElements'' is true
* **topLevel**: Array - always filled in by the "top level elements"
* **rememberProblems**: boolean; false: should the issues be recorded in ''problems'' argument
* **problems**: Array - problems registry

==== Methods ====

=== calcPrototypes: function() ===
Scans the tree, but returns ''options'' of elements instead of instantiating them. Same as this.build(true)

=== calcViewPrototypes: function(forElementOrPrototype) ===
Scans the DOM tree solely to search the ''options'' of the Views. Returns Array with null or several ''options''. If ''forElementOrPrototype'' is provided, **id** from there will be used to locate only views that are relevant to that ''id'', and ignore others. **Behaves in a way, as if the nodes of ''selector'' are located inside the node relevant to the provided element.**

=== build: function(prototypesOnly) ===
Scans the DOM tree; returns elements or their ''options'' (if the ''prototypesOnly'' is TRUE).

=== clear() ===
"Resets" the Builder state (elements, topLevel, problems) to a blank state.

===== Specifics of Elements and Views instantiation =====

In the Amm, Elements are not required to have Views. The Views are not required to be related to DOM nodes, although in the basic implementation they are usually related to working with the DOM and are descendants of Amm.View.Html.

Regarding the Html Views, the element can have related nodes scattered around the whole document tree, and they are **not** necessarily required to be grouped in a common place. Also in some cases Elements can have no DOM nodes. (The most simple case is the absence of the Views.)

In the Amm, the Element isn't usually aware of its Views, despite some helpers such as Amm.Element.prototype.findView() and used in the "widgets" constructDefaultViews() method; Views are subscribed to the Elements and observe its properties and events, and, in most cases, are oblivious to each other. Exception is the case, when views should juggle a common resource, such as input focus: when the element has several views, only one can be focused, obviously. // TODO: add a class for managing shared resources - 08.10.26

Views have requirements to the class of the element in the form of the Interface, which implies the Element has particular Traits. Most Traits don't make sense without the complementing View (of course, being part of the Element, they are still not view-aware), and a View that is built to observe a particular interface, such as Field, won't work without Traits that implement it. Therefore, most declarations are done in pairs: adding both specific Trait to the Element, and the View aware of that Trait.

Since some Views expect only one type of Trait, there is a method View.prototype.getSuggestedTraits(), which tells the Builder which Traits should be added to the built element's definition.

The element building is done in this sequence:
* instance of the Element with the necessary Traits
* instances of Views that receive both Element instance and the DOM nodes.

For convenience, view definitions or view instances can be provided in ''views'' key of the Element's constructor ''options'' hash.

Despite the View needs both Element and the DOM node in most cases for proper functioning, they can be provided to the view instance some time **after** it is created. Plus, theoretically the View can be detached from one Element and attached to another, same for the DOM nodes, but such a feature is not used often; also, View can exist without the Element, it just won't be updated.

So there are two approaches to creating the Elements:

* View first: define DOM nodes, that define the Views; Views define, what Traits are needed; Element is then created with the necessary Traits and options.
* Element first: we create Element instance, call its constructDefaultViews, and create views. In that case getDefaultTraits() cannot be used, and the Traits must be specified in the constructor options.
